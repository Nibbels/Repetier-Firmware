### Preparation findings

Read [Task0005 contract](Task0005.md), [historical DOWN→UP workflow](../../docs/z-offset/history-and-workflows.md), and relevant UI, EEPROM, ZOffset sources. The existing separation between menu table, formatting, setting owner, actions and persistence already provides the required behavior. Do not restructure the implementation merely to reduce line counts. Retain the usage page and both LCD widths.

**Preheat:** Configuration -> Preheat profiles exposes A bed, A extruder, B bed, B extruder; Extruder menu exposes A and B activation. These are user-editable material-neutral presets, not a hard-coded PLA/ABS binding. Factory values A=60/180 C, B=100/210 C. Bed edit permits off (0) or 50–160 C; hotend off or 70–270 C. The owner validates, the four int16 slots 1970/1972/1974/1976 and tag 1966 (0x50524831) remain stable. Each changed UI edit calls storePreheatProfiles and recomputes additive checksum at 104; no-op edits do not store. Activation requests both configured temperatures (hotend request for all extruders) without changing EEPROM. Do not add duplicate PLA/ABS state or renumber the existing IDs. Material labels could be changed separately only if specifically desired.

**LCD:** RF1000 4x16, RF2000 family 4x20 with different selector glyph. Actual parse/addInt, menu macros, adjustMenuPos, refreshPage and printRow exercised for all four editable entries and both quick action entries, including selector/selected marker, padding, LCD row address and cache. Tests include distinct modified values, maximum-width values and all four independent saturation/zero/minimum transitions. Max quick labels are 'A B160 E270' (16 columns) / 'A Bed 160 Ext 270' (20 columns); including cursor they occupy 12/18 columns respectively, no clipping or horizontal scrolling required. All four settings labels fit. Parent menu links and page/key mappings checked in source; the host replay uses a reduced two-entry quick-menu window, not an exhaustive navigation/encoder/debounce simulation. Existing ui-numbers and print-usage tests supplement this.

**Z DOWN→UP:** actual physical-key action mappings E2=DOWN, E1=UP and mainSwitchCase dispatch: only level 0/page index 1 modifies the offset; elsewhere the real action calls moveZAction with +1/-1. Replay uses actual ZOffset, zOffsetPlusAction/MinusAction, storeManualZOffset, and checksum. With 200 um live and 0 manual, 40 complete DOWN→UP pairs transfer all 200 um into persisted manual; after each pair effective steps return to original value. DOWN writes changed int32 manual offset at 1038 and checksum 104; UP with sufficient live offset does not write. No live SenseOffset, threshold 1908 or preheat bytes persisted by transfer. Checks include insufficient live remainder (2 um), zero crossing, upper manual clamp, simulated reload (manual retained, live cleared), and page/submenu jog routing without EEPROM mutation. The transfer is approximate at zero-snap/clamp boundaries or when asynchronous SenseOffset learns between keypresses. Do not replace this behavior with symmetric manual steps or reset SenseOffset on UI edits.
