# Research: persistent fault/event log, separate from settings

Date 2026-11-27; owner requests simple G-code-readable persistent error/problem history, possibly replacing emergency RAM records, no elaborate checksum scheme. This is a feasibility decision, not a production feature or address reservation. No hardware run/flash/merge.

## Comparison

1. RAM only (status quo): immediate report, no EEPROM writes, evidence lost at reset/power-off.
2. EEPROM only with synchronous append: theoretically less static data but blocks foreground around 112 ms for 33 byte-program operations (3.4 ms typical), competes with thermal service/serial and watchdog; cannot capture first event without transient RAM; REJECT.
3. Hybrid asynchronous persistent history: preserve active latch/masks, invalid episodes and first/first-fire evidence; in terminal mode or other explicitly bounded safe service, serialize records on demand from existing evidence one byte at a time when EEPROM ready. No new 32-B permanent mirror or queue. First step yields persistence, **no claimed SRAM reduction**, a few bytes of writer/reader state may be added. In normal printing no writes and preferably no additional hot-path service other than a cheap pending test or entirely terminal-only dispatch; do not log every temperature reading/PID iteration. After proof, optimize diagnostic storage separately (e.g. quantized signed 16-bit deci-C for four fields, 16 B gain across two snapshots; invalid-episode target 6 B gain across three heaters). Keep controller and safety calculations float/unmodified. Avoid dedicated 2x32 B staging buffers; a single staging record cannot guarantee preserving both first and first-fire if second arrives before first commit. A hypothetical design eliminating both 35 B snapshots but needing one 32 B staging buffer and 6–12 B state nets only 26–32 B before second pending event or other metadata; two staging records nearly cancel savings. Do not remove live evidence until replacement proves equivalent. Do not read EEPROM for LCD fault severity, lease, watchdog feed, heat/motion admission, or critical revocation. No RAM saving claims until all four builds and callchain analysis.

## Minimal format candidate (not fixed ABI)

32-byte binary diagnostic entry, explicit little-endian fields (not raw C++ object).
- 1 byte committed marker; 1 byte version.
- 4 byte monotonically advancing sequence (wrap-safe comparison, scanned from slots; no frequently written global head pointer).
- 4 byte uptime ms, 4 byte observation window ms.
- 4 x signed int16_t diagnostic temperature/delta/threshold in tenths (8 bytes; actual units/range and unknown handling must be validated; if threshold not a temperature, encode documented unit per event type, not silently quantize).
- 2 byte raw ADC, 5 bytes requested/admitted PWM/sensor/power limit/profile, 2 byte validity mask, 1 byte cause/channel encoded (fixed, stable IDs; include system and future event families without ambiguous values).
Total 32 B. No text storage; labels in Flash. Uptime is not calendar time; host may timestamp retrieval/receipt; do not invent absolute time. Generalize event IDs and units only as needed. Candidate slot counts 8/16/24 =256/512/768 B. 16 slots (512 B) would leave 608 B of current 1120 B tentative reserve for settings journal/future work; 0x0E00..0x0FFF is an illustrative possible range only, NOT allocated; owner of EEPROM settings must confirm journal needs and collision-free zoning. Old firmware ordinary bank remains untouched; arbitrary legacy M206 raw writes or upload erase may still touch/destroy upper bank. M502/new defaults should not erase independent log; explicit log clear separately, if wanted. Never expose raw generic writes to the region.

No CRC for diagnostic-only events (not safety settings). Use small version+commit marker and bounds/plausibility checks: overwrite ring slot by marking invalid and confirming completion, write 31 payload bytes, then write committed marker last and await completion before considering visible. 33 worst-case changed byte programming operations ~112.2 ms typical wall time; if unchanged bytes skipped or first virgin slot invalidation skipped, less. One service invocation launches at most one byte when ready and returns without waiting; complete time depends on service cadence (only 100ms thermal ticks would be up to ~3.3s, so use eligible foreground visits after thermal service, not ISR). If interrupted, old entry can be lost when overwritten and new entry can be incomplete/missing; accepted best-effort history. No CRC means arbitrary bit corruption can still look plausible; label log unverified/diagnostic and never drive safety or configuration from it. Atomic marker is only a simple publication convention, not a power-loss proof. Do not delay reset/off/watchdog or feed watchdog merely to finish log. Record watchdog/reset cause next boot where reset-recovery witness exists; cannot reconstruct missing pre-reset ADC/duty. Log only confirmed event onset, escalation/new unique issue or explicit rate-limited diagnostic; do not repeatedly log latched fault or every boot without new event. For 16 rotating slots and two writes to marker per reuse, idealized wear arithmetic ~800000 full append events before 100000 marker operations/slot, not a physical lifetime guarantee.

## Access and coexistence

Propose a dedicated unused G-code after checking M-code inventory, not M205/M206 raw EEPROM access or M115 handshake; names illustrative: list retained events newest/oldest ordered by sequence; optional limit/start; summary counts/problem list derived by scan; optional explicit clear (not automatic). Read-only available after normal reboot and via permitted terminal command, no unlock or target changes. During active print either reject/defer query or serve bounded chunks with queue/serial backpressure; no blocking on EEPROM busy. No full mirror: read one field/one record in a bounded scratch buffer only when needed. Continue immediate host-cancel and emergency live/first error report without waiting for log commit. In-progress settings transaction has exclusive EEPROM ownership; log waits until bus released/transaction safe (existing checksum yields may re-enter periodic services). No log from ISR; shared EEPROM access owner must serialize EEAR/EEDR/EECR, readiness and actual region addresses, never write legacy settings or corrupt journal. Log must not affect settings CRCs, validity, migration, recommissioning, safety limit or watchdog feed. If log cannot commit, heating remains inhibited; report log loss best effort. No automatic replay as new live fault.

## Decision and gates

Prefer hybrid diagnostic feature AFTER current safety/EEPROM architecture gates; EEPROM persistence is useful even with zero initial SRAM savings, not faster than RAM and not justified solely for SRAM. Simple record/version/commit marker and small ring, no CRC or general transaction system for logs. Keep settings integrity architecture separate. First stage reuse existing evidence without extra buffers; then measure compact snapshots, optional direct read of committed history and actual static/stack/flash/timing deltas. Validate ordering/wrap, full ring, overwrite, reset at each byte (including torn marker/payload), all-erased and corrupted entries, no settings overlap, busy/reentrant writes, missing host, continuous traffic, both first+first-fire before commit, watchdog reset and brownout best effort, no hot-path read/write, no safety regressions. Hosted GitHub CI with all host replays and four AVR builds is the project toolchain; no hardware experiment. Do not reserve address or M-code yet; handoff to Task0034 EEPROM/settings owner. No production logger implemented.


## Owner decision 2026-11-27 — use a persistent event log to simplify existing error handling

The owner approves a generic EEPROM log, even if it initially saves no SRAM. The primary benefit is **consolidation and deletion of bespoke error handling**, not a new suite of UI features. This supersedes the earlier feasibility-only decision; exact implementation remains with the exclusive Task0034/EEPROM owner.

Separate three responsibilities:
1. Detection and immediate safety response: retain each fault's specific detection, debounce, inhibit, severity, print/actuator response and recovery conditions. No EEPROM dependence or waiting for the logger. Keep unmistakable FIRE WARNING / WATCHDOG RESET where appropriate, immediate host cancellation and protocol-required responses.
2. One central diagnostic event admission path: stable numeric reason, channel/context, severity and captured evidence; deduplicate occurrences/episode transitions, retain first cause and first fire escalation, append best effort asynchronously. No per-module text formatting, modal dialog, raw EEPROM access or ad hoc acknowledgement state just for explanation. A lost log entry must not hide an active severe fault.
3. Shared diagnostic presentation: short generic message for ordinary diagnosed faults (e.g. ERROR DETECTED / SEE ERROR LOG), one reusable event decoder/formatter with Flash strings, read-only G-code log retrieval. Preserve live temperature/host compatibility and any existing operator response that is genuinely needed for safety or completing an operation. Historical events are not active faults; showing/clearing history must not acknowledge or release a safety latch.

First inventory existing error paths (thermal/autotune, EEPROM/settings, DMS, scan, motion, serial/driver); classify terminal fault, recoverable operation failure, transient warning, protocol response and normal status. Replace only redundant diagnostic text/UI/serial reporting, not functional reactions or protocol handshakes. Start with thermal emergency as the initial consumer, no repo-wide parallel production refactor. Measure actual deletions, shared-format costs, static SRAM/stack/Flash and interrupt/foreground gaps versus the verified baseline. Use the existing GitHub Actions pipeline for all four builds and host replays. A generic LCD error-log submenu, delete/acknowledge UI, filtering and other convenience features are explicitly deferred, not required for initial integration. No logging every polling tick, no write on ordinary status, no log-as-safety-authority. No hardware runs, flashing or merge authorized by this decision.
