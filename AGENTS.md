## 1. Mandatory startup and execution contract

**GitHub Actions first — mandatory for every worker.** The canonical build, test and measurement environment is the existing GitHub Actions pipeline **RFx000 firmware / Host replays and four AVR builds** (RF1000, RF2000, RF2000v2, RF2000-X44). Use GitHub repository/PR tools to commit, trigger the existing pipeline, inspect workflow runs and job logs, and retrieve the evidence archive (ELF/HEX/map/disassembly/resources). **No local checkout, AVR toolchain, Arduino CLI, compiler or container network access is required. Their absence is NOT a blocker.** Local tests are optional diagnostics, not a prerequisite or substitute. Do not ask the owner to install or run tools merely because local execution is unavailable. Use an additional task-private CI workflow only if the existing pipeline cannot execute an otherwise required task-private test; never duplicate or replace the standard pipeline. Empty run discovery, queued/pending jobs or cancelled obsolete revisions are not CI failure: check the latest PR head again, inspect jobs/logs and continue independent work. Record exact PR head, tested merge SHA, run, artifact and test result; do not claim unrun tests passed. See [CI contract](coordination/TASKS.md#firmware-pr-checks).

**Start here for every task:** (1) read this file, [coordination/TASKS.md](coordination/TASKS.md) and your task file; managers also read [MANAGER_HANDOVER.md](coordination/MANAGER_HANDOVER.md); (2) verify live target HEAD, existing task branch/PR and active write ownership; (3) read the relevant sections of the [firmware module reference](docs/firmware-worker-reference.md) and linked mechanism docs; (4) work in small commits on the assigned branch and use GitHub Actions for evidence. Live repository state and current owner instructions outrank historical chat summaries and historical task statuses. No hardware experiments or flashing without separate owner approval.

**Parallel worker tasks.** Read [coordination/TASKS.md](coordination/TASKS.md) before starting refactoring work. It defines the active waves, exclusive write scopes, shared-file integration and worker self-merge protocol. Work on the assigned task branch; merge only to `ai-firmware-review` after the task checks pass. Workers update their own task file, not the shared index.

**Git workflow:** `ai-firmware-review` is the isolated working branch; keep `community_development` unchanged until specifically instructed. The DRV8711 BLANK invalid read command was removed without changing actual default electrical timings in [commit 8f00ed8](https://github.com/Nibbels/Repetier-Firmware/commit/8f00ed8df6a0e825dee368c1233ffc4934349faa).

**Owner-facing command safety (owner, 2026-11-28; mandatory for all workers and managers).** Only present an executable/copyable shell, Git, PowerShell, G-code or other command to the owner when the owner should execute it now and all prerequisites have been verified against the live state. Explicitly say what to execute now. Never put deferred, conditional, illustrative, unsafe or not-yet-authorized commands into a runnable/copyable code block or command field, even when accompanied by a warning. Describe future actions and their prerequisites in ordinary prose instead, without printing the command. If showing a deferred command is genuinely necessary, show it only as visibly commented-out plain prose outside any code block or copyable command field; comment every executable line using the appropriate comment syntax. Recheck destructive actions (especially branch deletion) immediately before recommending them; do not combine eligible and ineligible targets. Prefer performing authorized actions through available repository tools and reporting the result. A future cleanup plan is not an instruction to execute it now.

For future chats: read this file and the mechanism docs, verify against code and changelog, distinguish verified behavior from hypotheses, then propose isolated changes and tests rather than guessing.

## 2. Current priorities and invariant safety rules

**P0 owner decision (2026-11-25): [Task0034](coordination/tasks/Task0034.md) takes precedence over motion packing and UART production changes.** Prevent sustained heater power after loss of thermal progress; require bounded, expiring authorization and no stale rearming, including maximum duty. Hardware-independent fail-off where possible; never claim safety from interrupt priority alone. No hardware tests without separate approval.

**Heater safety and watchdog.** Scan and motion waits must keep periodic services running. Read the [heater safety and watchdog requirements](docs/heater-safety.md) before changing heater control, PWM, scheduler waits or scan state dispatch.

**Non-negotiable operator workflow:** In Mod Menu page 2 the Z/bed DOWN→UP button pair intentionally transfers 5 µm of live SenseOffset into the EEPROM-backed manual part of `Printer::zOffset` with approximately unchanged final clearance (see [live takeover procedure](docs/z-offset/history-and-workflows.md) and the original January 2017 changelog). Do not “fix” the asymmetric button behavior or reset dynamic offsets while a manual transfer is underway.

**Authoritative LCD geometry (owner clarification, 2026-11-27).** All supported stock configurations have **four LCD rows**: RF1000 = **16 columns × 4 rows (16×4)**; RF2000, RF2000v2 and RF2000-X44 = **20 columns × 4 rows (20×4)**. See [`Repetier/ui.h`](Repetier/ui.h): `UI_ROWS = 4`, board-specific `UI_COLS = 16/20`. Only these four-row geometries are supported, including in renderer tests. Remove obsolete alternative-row branches and fixtures; do not treat historical assumptions or stale summaries as hardware facts. Verify `UI_ROWS` and `UI_COLS` before any display layout, replay or hardware description; test the actual 16×4 and 20×4 builds.

This is shared AVR/ATmega2560 Repetier firmware for **RF1000, RF2000 and RF2000v2**. Motion planning, SenseOffset and bed correction are common code. Do not apply model-only changes without a demonstrated model-specific cause. Stepper timing and SRAM/flash limits matter; avoid expensive arithmetic in ISRs.

**Board connectors and retrofits.** Preserve named physical connector definitions and the existing controls for available switched outputs. A port can be unused in the factory build and used for equipment such as an E3D V6 or Volcano heatsink fan or a water-cooling pump. The RF2000 family shares its pin map and configuration with model-specific defaults. Check the [board notes and X44 example](docs/board-connectors.md) before changing pin assignments or retiring an output path.

## 3. Engineering and resource policy

**Development roadmap.** Build firmware for the RFx000 boards with the established Repetier serial printing interface. Give each service ownership of its mutable state and use small, verifiable commits. Evaluate step packing in the motion smoothness and performance block. [Development blocks](docs/development-roadmap.md) · [Maintenance tasks](docs/maintenance-tasks.md)

**Resource and compiler optimization policy (owner, 2026-11-25).** For every cleanup, refactoring and optimization task, apply this policy wherever resource or performance trade-offs are relevant; it does not expand the task's write scope. Prioritize runtime speed, predictable interrupt/service latency and free SRAM over a smaller firmware image, subject to correctness and safety. Prefer spending available Flash to reduce SRAM use (including static data, stack peaks and any heap/buffer use) or improve measured runtime performance. Keep SRAM headroom for motion queue slots, communication buffers and stack/interrupt nesting; do not introduce unnecessary dynamic allocation or heap fragmentation. Store immutable data in Flash where practical, using correct AVR near/far Flash access and checking hot-path cost. Do not optimize for Flash size alone while sufficient application Flash remains; track the bootloader boundary and preserve capacity for future functionality. Compiler/linker choices should optimize measured execution speed rather than smallest image size: benchmark -O2/-O3, selective options and the existing baseline, including worst-case ISR latency, SRAM/stack and Flash for all four supported builds. Select the fastest safe measured candidate within memory and timing constraints, not a blanket flag change. Record relevant trade-offs and evidence; a measured no-change result is valid. Revisit SRAM-to-Flash opportunities and actual stack headroom in the final optimization audit. This is a resource priority, not a mandate to fill Flash without a concrete benefit.

**Interrupt-mask policy (owner, 2026-11-28; mandatory).** Use interrupt masking only for a demonstrated atomicity or exclusive hardware-access requirement. Prefer single-owner state, safe admission, unmasked preparation and the shortest coherent publication. No blocking I/O, waits for interrupt-driven progress or unbounded work under a mask; move expensive computation and reporting outside. Preserve prior SREG state, necessary atomic multi-byte snapshots, shared GPIO/register ownership, ISR exclusion and timing. For retained masks document the invariant, competing contexts and finite linked worst-case duration; account for transitive/nested continuous blackout and selective vector masking. Apply this now in each active worker's scope; do not postpone safety defects. [Task0036](coordination/tasks/Task0036.md) mandates whole-firmware closure after Task0034 and Task0032 integration, before final software release qualification, with four-image linked inventory and global response evidence. No competing production worker during P0 or Task0032.

**Motion performance.** Optimize sustainable print speed and worst-case service gaps together. **Quality-first packing (owner, 2026-11-25):** [Task0032](coordination/tasks/Task0032.md) is the primary remaining print-core optimization objective. Preserve configured physical microsteps and use the smallest feasible packing group consistent with measured processor demand, bounded interrupt/service latency and fail-safe heater/watchdog behavior. Derive the policy from real workload classes and foreground budget, not guessed thresholds, average idle time or peak pulse rate. Do not reduce microsteps automatically or remove timing guards without proof. Remove manual DblFq adjustment only after a validated replacement; preserve legacy EEPROM/protocol compatibility. **Simulation first:** exhaust reproducible software simulations/emulation, including G-code density/throughput and concurrent maintenance demand, before any printer experiment. Hardware acceptance remains explicitly deferred until separate owner approval. Put timing, workload generation and result analysis in versioned scripts; T14 and ALUBUTYL are optional compute workers after checking access. Do not require the owner to manually analyze complex runs. Use the [timing plan](docs/motion-timing.md) for STEP/DIR ownership, Advance handoffs, UART throughput and the baseline required to evaluate packing. Use the [planner notes](docs/motion-timing.md#lookahead-short-moves-and-extrusion-transitions) when touching short-segment speed, retract or print–travel joins. Preserve their behavior during structural refactors and review the speed policy with its own replays.
